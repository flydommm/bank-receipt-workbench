## 根因与修改

1. **页面预览反复启动 Python。** 原有 `render_page`、`inspect_pdf` 和 `batch_snapshot` 每次都启动并退出引擎，重复支付导入成本。现在这三个短操作共用一个 JSONL 引擎进程；分析、长检查和写操作保留各自的原有路径。排队上限为 8，仍受宿主总计 3 个引擎进程的限制，给任务和写操作留下两个名额。
2. **同一页的版式描述重复计算。** `BatchPdfSource` 和 `SourceLayoutIndex` 分别描述同一页。现在二者共用当前私有 PDF 生命周期内的匿名版式描述；关闭、恢复或重新打开来源时重建，不跨来源复用，不保留位图或页面句柄。
3. **像素比较存在大量 Python 临时分配。** 颜色跨度与可见图形误差比较改为等价的通道差和字节运算，保留原有阈值以及每页实际可见图形检查。

读进程只复用已导入的模块，不缓存 PDF 响应或数据库快照。每次渲染仍重新制作、核验 SHA 绑定的私有来源副本，数据库查询仍重新打开连接。坏响应、断管和超时会回收该进程，后续请求重新启动；失败请求不会自动重放。退出时回收进程树并唤醒等待者。

M04 的断网卸载/重新安装、原件与命中片段应用内缩放、首页/原件/整页微调/导出预览已通过；WebView2 缺失及 Windows 系统高 DPI 未获本轮反馈。M26 文件数量、字节数及 SHA-256 前后一致，用户确认通过。实际验收状态以[人工测试清单](manual-test-checklist.md)为准。

本轮只读排查确认如下调用关系，尚未实施新的结果载入优化：

1. “载入结果中”由 `receiptReviewBusy` 显示，覆盖准备审核、按每批 200 条串行读取并验证所有审核结果，以及提交来源导航状态；PDF 页面渲染不在这段忙状态内。
2. 每批审核结果读取都会调用 `BatchStore.review_snapshot`，从全部持久化页面重建并核对任务清单，再验证已保存审核记录。返回页的容量检查还逐项序列化逐渐增长的结果列表。这些校验用于阻止过期或不一致的结果；后续优化必须保留其完整性约束。
3. 0.1.36 的复用进程只处理 `render_page`、`inspect_pdf`、`batch_snapshot`。准备审核及审核分页仍走单次进程调用，因此分页间还有引擎启动成本。
4. 本机 Bun 用 2,000 个合法合成片段、每批 200 条进行三轮前端解析，分别约 263 / 242 / 231 ms。该测量不包含 IPC、后端或 WebView 绘制，不能代替干净 Windows 计时；现有证据应优先排查后端工作，而不是把逐条 SHA 校验直接认定为分钟级等待根因。

另用既有私有 HX-A 测试任务的独立 SQLite 副本，对底层 `review_snapshot` 采样：一次读取包含 671 页检查，采样器累计记录约 2,879 万次函数调用，主要消耗在 JSON 校验及清单重建。此任务的计算版本已旧，完整准备审核被正常拒绝；未绕过版本校验，也未将该次底层采样作为 0.1.36 完整载入基准。原私有来源副本哈希保持不变，诊断数据仅保存在忽略目录。

下一步应以当前计算版本的独立任务测量准备、每批读取和完整界面载入，再验证减少重复编码或同请求重复工作的效果。不能用跨请求保留未经重新核验的快照来直接省略来源、修订或审核校验。本段定位证据不计为已修复或新安装包性能验收。
