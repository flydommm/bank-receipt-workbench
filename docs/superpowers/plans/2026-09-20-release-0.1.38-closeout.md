# 0.1.38 集中修复与定向验收计划

## 目标与边界

用户已开启目标模式，授权子代理驱动、必要提交、统一打包及远端干净 Windows 定向验收。目标版本为下一补丁版 0.1.38 Core x64 NSIS，保持 M01–M35 编号；0.1.37 已通过操作保留，不从头重测。源码推送和公开发布不在本轮授权内。

本轮必须解决三个已确认问题：HX-A 第 34 页空白误候选；结果载入及校准保存、撤销长等待；撤销动作显示保存文案。用户已补齐远端 MS-A 和 SH-A，后续核对并使用。业务原件只读，真实样本/路径/正文及诊断输出只放忽略目录；加工前建立独立副本并记录大小和 SHA-256，处理后核对原件。

## 分工与依赖

1. 检测代理负责 `engine` 中回单检测与候选生成模块及对应 `tests`：复现 HX-A 第 34 页，对照普通三栏、669 页和671页；以内容证据修复，禁止页码或银行名特判。先报告实际根因及精确拟改文件，避免与管理路径重叠。
2. 性能代理负责批次管理/审核分页/快照及校准管理模块、必要的 `src-tauri` 管理调用层和前端服务：沿 `snapshot → prepareReview → reviewPage` 及保存/撤销后的 reload 计时，减少证据支持的重复工作。不得仅增大超时，不放松源文件身份、结果版本、审核一致性和输出权限校验。若引入缓存，必须验证源变化、数据库/版本变化及异常失效。
3. UI 代理负责 `src/services/receiptCalibrationController.ts`、`src/components/ReceiptCalibrationWorkspace.tsx` 及两个对应测试文件：区分保存与撤销动作，成功提示必须在权威返回和结果重载之后；失败或丢响应保持待核实并重试同一动作，旧会话迟到结果不得覆盖新会话。
4. 主代理负责范围与集成决定、计划/测试记录、版本元数据、审查、提交、构建与远端验收。共享工作树中的既有文档改动保留；各代理不得自行提交或修改他人所有权文件。

## 验证与交付顺序

- 首先建立旧版可重复证据；性能记录分阶段耗时或确定性的调用次数，不把远程画面抽样当精确基准。
- 每个修复运行直接相关的 pytest/Vitest 回归；主代理审查实际差异和测试输出。集成后运行 TypeScript/Vite 与受影响 Rust/引擎协议检查。安全/一致性边界变化需专项审查。
- 确认样本几何与原件哈希；对大任务完整流程作前后同条件比较。正确性失败或无法解释的缓存一致性问题须先解决。
- 同步 `package.json`、Cargo/Tauri、引擎及帮助版本。将已验证修复、版本和本轮记录按需提交，确保发布构建输入固定且干净。
- 使用 `scripts/build-release.ps1 -Edition Core` 统一构建；按既有交付流程核对安装资源、私有运行库、健康版本、合成 PDF 冒烟及安装包大小/SHA-256。保留上一稳定安装包作回滚，不覆盖既有产物。
- 将安装包交付远端，默认目录升级并核对版本。通过 UU 使用受控 PDF 副本，定向复测：空白页/三栏/双栏尾页、长等待流程、撤销恢复及文案、待复核门控与导出；补同银行跨文件、历史版式复用/重启、特殊单证等未完成关键场景。
- 更新当前验收表和交付记录，附可在干净系统阅读的 PDF 清单。通过、失败、未测分开；无法覆盖的环境条件明确说明，禁止以自动化测试替代远端 GUI 验收。

## 完成条件

三项缺陷有可审查修复和针对性回归；实际 NSIS 与源码提交对应；远端修复关联关键流程已完成定向验收，剩余条件项目有明确结论和限制。若验收再发现实质缺陷，保留证据并继续修复，不能为坚持“一次打包”交付已知错误包，也不能提前把目标标记完成。
