## 第一次外部 PR 前的基线

- [ ] 已阅读 [README](../README.md)、[CONTRIBUTING.md](../CONTRIBUTING.md)、[第三方组件说明](../THIRD_PARTY_NOTICES.md)、根目录 [LICENSE](../LICENSE)、根目录 [DCO](../DCO) 和 [SECURITY.md](../SECURITY.md)。
- [ ] 已核查 GitHub `main` 的实际保护规则、ruleset 和必需检查状态；仓库里有工作流文件不能替代远端核查。
- [ ] 已按现有第三方清单建立来源、版本、原许可证、文件通知和兼容性记录；未核实项目明确列为待处理。
- [ ] 已确认现有 `.github/workflows/ci.yml` 的检查名称为 `Windows verification`。
- [ ] 已准备维护者记录，用于保存 PR 讨论、审查结论、验证结果和已核验 SHA。

### DCO 工作流合同

工作流路径为 `.github/workflows/dco.yml`，对外必需的 commit-status context 为 `DCO`。工作流使用 `pull_request_target`，内部 Actions job 显示为 `Check DCO`，结果明确写入被审查 PR head 的 `DCO` status。配置必需检查时选择 `DCO`，不能用内部 job 名代替。维护者首次基线时确认：

- [ ] 工作流只执行可信 base 代码，不执行 PR head 中不可信的工作流代码。
- [ ] 工作流通过 Pull Request API 分页读取全部提交；每个 PR 最多 250 个提交，超过范围必须失败并要求拆分 PR。
- [ ] 对每个提交的 Git author 和每个 `Co-authored-by` 共同作者，检查与姓名、邮箱匹配的 `Signed-off-by`；姓名允许 Unicode 和正常空白，邮箱比较不区分大小写。
- [ ] `Signed-off-by` 与 `Co-authored-by` 位于提交消息结尾的独立、连续 trailer 段；正文中的同名文本不计入。
- [ ] 分页失败、响应不完整、提交超出 API 可验证范围或无法证明读完全部提交时，DCO 状态失败；不设置机器人、维护者或合并提交豁免。
- [ ] 已记录自动检查的边界：它只能核对提交记录，不能证明真实身份、雇主授权或版权权属。

## 每次合并前：当前 PR 检查

### 变更和敏感数据

- [ ] 已阅读当前 PR 描述、Issue、完整 diff 以及新增的二进制、图片、文档和夹具，确认用户问题、影响范围和兼容性影响。
- [ ] 提交、截图、日志、测试夹具和生成文件没有真实银行材料、真实账号、客户信息、业务 PDF、识别文字、令牌、环境变量值、私有缓存或不必要的本机路径。
- [ ] 复现使用合成数据、公开夹具或临时生成文件；文档链接指向公开位置或正确的仓库相对路径。
- [ ] 如使用 AI 辅助，贡献者已自行检查来源许可、事实和代码正确性；没有把 AI 当作签署人或权利保证人。

### 来源、权限和许可证

- [ ] 贡献者确认有权提交原创内容并保留其版权；涉及雇佣、委托或其他合同的，已取得雇主或合同相对方所需授权。
- [ ] 本次有权许可的原创贡献按 [AGPL-3.0-only](../LICENSE) 提供；无需版权转让或额外专有再许可。本项目不因 PR 自动取得专有再许可权，也不要求 CLA。
- [ ] 本 PR 新增或变更的第三方代码、依赖、图片、字体、文档和测试夹具均列出来源链接、版本或提交、原许可证、受影响文件或目录，以及许可证文本和版权通知位置。
- [ ] 已检查兼容性并按原许可证保留第三方通知；必要时更新 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)，没有把第三方材料改标为项目许可证或重新许可。
- [ ] 来源、版本或许可证不清楚时已请求补充或拒绝合并；没有盲目代签。已有历史来源不因存在于旧提交中就自动合格，若本次变更涉及它则重新核实。

### DCO 与 Windows 验证

- [ ] 当前 PR head 的 `DCO` status 成功，且对应当前已核验的 head SHA；超过 250 个提交、状态缺失、失败或无法确认 API 已读取完整提交时不合并。
- [ ] 已确认每个提交的 author 和每个共同作者均有匹配的 `Signed-off-by` 独立连续末尾 trailer；GitHub 隐私 `noreply` 邮箱仅在与提交中 Git 身份一致时接受。不得要求身份证号或住址，签署信息会随 Git 历史永久公开。
- [ ] 当前 PR 对应的 `Windows verification` 已通过（可运行在该 head 生成的合并测试提交上）；不能用旧版本、本地启动或非 Windows 测试替代。
- [ ] DCO 通过仅表示提交记录匹配，仍完成了本页的权限和第三方来源人工审查；维护者没有替别人签名、批量补签或盲目重写历史。

## 远端规则启用与验收记录

以下是建议由维护者在 GitHub 远端设置的规则，最终状态必须以实际核查为准：

- [ ] 要求 Pull Request 合并。
- [ ] 将 `DCO` 和 `Windows verification` 设为必需检查。
- [ ] 限定检查来源为实际运行的 GitHub Actions，并要求分支保持最新；规则对管理员也生效，不通过常规管理员绕过来合并。
- [ ] 禁止强制推送和删除 `main`。
- [ ] 如果只有一名维护者，不因自己的 PR 强制额外一名审批而自锁；外部 PR 仍必须由 `flydommm` 实际审查。
- [ ] 已记录规则或 ruleset 名称、目标、enforcement、必需 context、启用时间和证据链接；没有把建议写成已启用状态。

启用顺序：

1. 先将经过审查的贡献文件和工作流发布到 `main`，使 DCO 检查能读取可信的主分支代码。已有 `main` 历史不批量补签或改写。
2. 用维护者的独立试验分支创建 PR，验证“缺少签署失败 → 本人补齐签署后通过”；修改 PR 提交后检查必须针对新的 SHA 重新运行。试验 PR 不合并，实际签署必须由有权贡献的人完成。
3. 在 GitHub 的 `main` 分支保护或 ruleset 中启用上述规则。`DCO` 应选已实际产生的状态，避免把 `Check DCO` 配成另一个永远缺失的必需检查。
4. 验证未签署 PR 确实不能合并、通过 DCO 和 Windows CI 的 PR 仍需维护者检查本页，再记录规则名称、启用时间、试验 PR 与工作流链接。

如果启用后配置有误，由仓库所有者在 Settings 修正规则；撤回本次贡献文件可用新的 revert 提交，不强制重写历史。调整规则期间继续暂停外部 PR 合并。远端实测完成后再更新本页“启用状态”，不能用本地测试替代 GitHub 验收。
